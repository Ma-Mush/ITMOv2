# Нагрузочное тестирование — план и спецификация сценариев

Этот документ представляет собой рабочий регламент и план нагрузочного тестирования сервиса. Он предназначен для инженеров по качеству, разработчиков и SRE-специалистов.

Цели документа:
- Обеспечить воспроизводимую методологию проверки производительности системы на разных этапах жизненного цикла.
- Покрыть ключевые паттерны пользовательского поведения и стрессовые режимы работы (включая емкостные тесты, спайки, длительную деградацию и работу с БД).
- Установить измеримые пороги качества (SLO/SLA) для каждого теста.
- Унифицировать сбор доказательной базы (Evidence) для принятия решений о готовности релиза.

Регламент использования:
1. Выбрать целевой сценарий в соответствии с текущей фазой тестирования (регресс, поиск предела, проверка утечек).
2. Запустить генератор нагрузки (k6 или locust) по заданным параметрам профиля.
3. Собрать телеметрию (APM, Grafana, логи, DB slow logs) и зафиксировать артефакты в столбце Evidence.
4. Оценить прохождение теста по критериям из колонки «Допустимый предел». В случае отклонений зафиксировать баг-репорт с профилем деградации.

| Capacity-200 | 200 rps, 10 минут | p95 ≤ 1.3s, p99 ≤ 2.2s, ошибок ≤ 1.5%, CPU pod ≤ 85% | Задержки обработки, паузы сборщика мусора (GC) | k6 run artifact, метрики JVM/Go GC pauses |

| Read-heavy | 100 rps, 10 минут (80% GET, 20% POST) | p95 ≤ 1.1s, ошибок ≤ 1%, Cache Hit Rate ≥ 80% | Эффективность кэширования, нагрузка на чтение | k6 custom metrics summary, Redis/Cache dashboard |
| Write-heavy | 50 rps, 10 минут (40% POST/PUT/DELETE) | p95 ≤ 1.5s, p99 ≤ 2.5s, ошибок ≤ 1%, DB lock wait ≤ 50ms | Блокировки таблиц/строк БД, дисковый IOPS | k6 report, PostgreSQL pg_stat_activity / lock metrics |
| Payload max | 20 rps, 10 минут с предельным размером body | p95 ≤ 1.3s, ошибок ≤ 1%, отсутствие HTTP 413/504 | Парсинг payload, сетевая пропускная способность | k6 metrics JSON, Nginx ingress logs (access/error) |
| N+1 / Heavy listing | 20 rps, 10 минут (запросы каталогов и фильтрации) | p95 ≤ 1.2s, число SQL-запросов на endpoint стабильно | Количество запросов к БД на транзакцию, CPU БД | Jaeger/OpenTelemetry traces, DB Query Analytics |

## Инструменты и фиксация Evidence

- Инструменты генерации нагрузки: `k6` или `locust`. Сценарии должны быть зафиксированы в репозитории кода тестов.
- Сбор телеметрии: Prometheus + Grafana, Jaeger/OpenTelemetry, логи Ingress/Nginx, системные метрики хостов и контейнеров.
- Стандарт Evidence:
  1. Ссылка или вложенный файл HTML/JSON отчёта запуска.
  2. Ссылка на snapshot дашборда Grafana с таймфреймом тестирования.
  3. Трассировка самого медленного запроса (p99+) при наличии APM.
  4. Вердикт: Pass / Fail с перечнем выявленных лимитов и узких мест.

## Критерии приемки

- Обязательные базовые тесты (Smoke, Baseline, Sustained-50, Capacity-100, Read-heavy, Write-heavy, Cold → Warm, Soak-60) должны строго укладываться в допустимые пределы без превышения лимитов.
- Исследовательские тесты (Spike, Stress ramp, Dependency delay) служат для определения запаса прочности системы; выход за пределы фиксирует предельную емкость архитектуры без выставления блокирующего статуса релизу при условии корректной изоляции сбоев.
