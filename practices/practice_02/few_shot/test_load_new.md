# Нагрузочное тестирование — план и сценарии

Этот файл описывает согласованный набор нагрузочных сценариев, их цели, метрики и допустимые пределы. Он нужен, чтобы:
- задать единый план проверок производительности и стабильности;
- повысить покрытие за счет разных профилей нагрузки (smoke, sustained, peak, stress, soak, spike, read/write);
- фиксировать артефакты Evidence (отчеты инструментов и метрики наблюдаемости) для повторяемости и аудита.

Как пользоваться:
- для каждого сценария запустить тест, собрать метрики и приложить ссылки/пути на отчеты в столбце Evidence;
- отметить факт прохождения по критериям «Допустимый предел»; при нарушении — завести задачу с найденными узкими местами;
- при необходимости адаптировать пороговые значения под актуальные SLO/неконфункциональные требования продукта.

## Сценарии и критерии

| Сценарий | Нагрузка и длительность | Допустимый предел | Что измеряем | Evidence |
|---|---|---|---|---|
| Smoke baseline | 10 rps, 1 минута | p95 ≤ 1.0s; ошибок ≤ 1% | Латентность p50/p95/p99, кодовые ошибки | Отчёт k6/locust; скриншот p95 |
| Baseline устойчивость | 10 rps, 10 минут | p95 ≤ 1.0s; ошибок ≤ 1%; дрейф p95 ≤ 10% | Латентность во времени, ошибки | k6 summary; Grafana панель latency/time |
| Sustained-50 | 50 rps, 10 минут | p95 ≤ 1.0s; ошибок ≤ 1%; CPU ≤ 70% | Латентность, ошибки, CPU/Memory | k6 report; Grafana CPU/Mem |
| Capacity-100 | 100 rps, 10 минут | p95 ≤ 1.2s; p99 ≤ 2.0s; ошибок ≤ 1%; CPU ≤ 80% | Латентность, ошибки, утилизация | k6 report; системные метрики |
| Capacity-200 | 200 rps, 10 минут | p95 ≤ 1.3s; p99 ≤ 2.2s; ошибок ≤ 1.5%; CPU ≤ 85% | Латентность, ошибки, GC паузы | k6; Grafana GC/CPU |
| Peak-500 | 500 rps, 5 минут | p95 ≤ 1.5s; ошибок ≤ 2%; нет деградации после теста | Латентность, ошибка, восстановление | k6; сравнение метрик «до/после» |
| Spike 5× | Спайк 100→500 rps, 60с, 3 цикла | ошибок ≤ 5% в спайке; восстановление p95 ≤ 1.2s за ≤ 30с | Восстановление после спайка | k6 сценарий spike; Grafana аннотации |
| Stress ramp | Рамп 0→1000 rps за 10 минут | Зафиксировать точку излома: p95 > 1.5s или ошибок > 2% или CPU ≥ 90% | Пропускная способность до деградации | k6 ramping; таблица «точка излома» |
| Soak-60 | 50 rps, 60 минут | ошибок ≤ 1%; рост памяти ≤ 5%; стабильная p95 (дрейф ≤ 10%) | Утечки, стабильность | k6 длительный отчет; Grafana Mem/GC |
| Read-heavy | 100 rps, 10 минут, 80% GET | p95 ≤ 1.1s; ошибок ≤ 1%; cache hit ≥ 80% | Латентность, ошибки, cache hit | k6; Grafana cache/dash |
| Write-heavy | 50 rps, 10 минут, 40% POST/PUT/DELETE | p95 ≤ 1.5s; p99 ≤ 2.5s; ошибок ≤ 1%; DB lock wait p95 ≤ 50ms | Латентность, ошибки, блокировки БД | k6; APM/DB slow log |
| Payload max | 20 rps, 10 минут, крупные payload | p95 ≤ 1.3s; ошибок ≤ 1%; нет 413/timeout | Влияние размера запроса | k6; nginx/app логи |
| N+1/листинги | 20 rps, 10 минут, «тяжелые» списки | p95 ≤ 1.2s; число DB-запросов/запрос стабильно | N+1, повторные запросы | APM traces; k6 thresholds |
| Cold → Warm | 50 rps, 5 минут (очищен кеш) | «Прогрев» ≤ 2 мин; после прогрева p95 ≤ 1.2s; ошибок ≤ 1% | Поведение при холодном старте | k6; Grafana cache warmup |
| Degradation tolerance | 50 rps, 10 минут, +100ms задержка БД | p95 ≤ 1.6s; ошибок ≤ 1%; нет каскадных таймаутов | Устойчивость к деградации | k6; fault-injection метки |

Примечания к метрикам:
- Латентность: фиксируем p50/p90/p95/p99, отдельно «server time» и «end-to-end» при наличии;
- Ошибки: совокупность HTTP 5xx и timeouts; 4xx не учитываем, если они ожидаемы профилем;
- Ресурсы: CPU, память (heap/rss), GC паузы, диск/сеть, пул соединений, lock wait/DB slow queries;
- Кеш: доля попаданий и объём кеша; для холодного старта фиксируем время стабилизации.

## Инструменты и артефакты

- Инструмент нагрузки: k6 или locust (любой один на проект). Храните HTML/JSON отчеты рядом с результатами прогона.
- Наблюдаемость: Grafana/Prometheus (снимок/ссылка панели с временными аннотациями теста), APM traces, DB slow log.
- Для каждого сценария в Evidence добавляйте ссылки на:
  1. отчет нагрузочного инструмента,
  2. скриншоты/экспорты ключевых метрик,
  3. краткий вывод Pass/Fail и замеченные узкие места.

## Критерии принятия

- Сценарии «Smoke», «Baseline», «Sustained-50», «Capacity-100», «Read-heavy», «Write-heavy», «Cold → Warm», «Soak-60» должны выполняться в пределах «Допустимый предел».
- «Spike» и «Stress ramp» используются для обнаружения границ: допускается временное ухудшение, но система должна восстанавливаться в заданные интервалы; фиксируется точка излома.
- Любые нарушения критериев — повод для заведения задач на оптимизацию с приложением Evidence.

История: документ расширяет и конкретизирует первоначальные проверки, добавляя больше сценариев и четкие количественные пороги без заглушек.
