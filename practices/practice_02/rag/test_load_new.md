# Нагрузочное тестирование — план на основе спецификации сервиса (RAG)

Документ определяет программу нагрузочного тестирования сервиса AI-помощника для ревью PR. Все сценарии, пороговые значения и ограничения сформированы строго на основе подтверждённых требований проекта (`practices/practice_01/context.md`, `CASE.md`, `tests_load.md`).

Назначение файла:
- Проверка соблюдения нефункциональных требований (SLO/SLA) под рабочей и предельной нагрузкой.
- Валидация правил надежности (REL-1), безопасности (SEC-1), контракта API (API-1) и формата ответа (OUT-1).
- Фиксация доказательств (Evidence) соответствия сервиса архитектурным ограничениям.

Порядок использования:
1. Выбрать сценарий из таблицы в зависимости от проверяемого правила сервиса.
2. Сгенерировать синтетический или реальный поток diff-файлов (с контролем длины и наличия секретов согласно правилам).
3. Запустить тест через k6/locust и зафиксировать артефакты в поле Evidence.
4. Оценить результат по колонке «Допустимый предел». Отклонение от правил REL-1/API-1/SEC-1/OUT-1 считается критическим дефектом.

## Инструменты и фиксация Evidence

- Инструменты генерации: k6 или locust со встроенными проверками JSON-схемы (OUT-1) и HTTP-кодов.
- Инструменты наблюдаемости: Grafana, Prometheus, Loki/Elasticsearch (для проверки OBS-1), Jaeger (для проверки задержки SEC-1).
- Состав Evidence:
  1. Отчет k6/locust с процентом соблюдения thresholds.
  2. Дашборд Grafana за интервал тестирования.
  3. Лог аудита санитизации (для подтверждения SEC-1 и OBS-1).
  4. Итог: Pass / Fail с привязкой к конкретным правилам.

## Критерии приемки

- Любое нарушение правил безопасности (SEC-1) или логирования (OBS-1) под нагрузкой является абсолютным блокером релиза.
- Превышение лимита таймаута REL-1 (>10s) или пропуск diff > 20k символов без HTTP 413 (API-1) квалифицируется как критический дефект.
- Базовые сценарии должны строго укладываться в p95 ≤ 1.0s при нагрузке до 50 rps.
